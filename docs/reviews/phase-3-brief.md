# Phase 3 brief — Smart capture (OCR, expiry parsing, Gemini)

Written 2026-10-24 by the Phase 3 build session (chain of sessions, D-091: no "go" is awaited).

## What this session builds (spec build order)
1. **Engine bake-off tooling and a provisional engine.** `scripts/ocr_bakeoff.py` runs every candidate (RapidOCR, EasyOCR, docTR, Tesseract) on `tests/fixtures/private/phase3/` at long edges 1024 and 1600 and writes the table the spec asks for (per field correct / partial / wrong, median and p95 latency, memory, weighted score, the 4 s rule). A separate `bakeoff` image target holds the heavy candidates so the app image stays small. The app runs RapidOCR (ONNX Runtime) until the measurement exists (D-099).
2. **Pipeline** `backend/app/integrations/ocr/`: resize, OCR lines with boxes and confidences, field extraction, proposals with `source`, `confidence`, `flags`. Runs in the one size-1 heavy executor (shared with image processing), never on the request thread. `POST /drafts/{id}/extract` answers 202; the client polls the draft. New drafts queue a local reading at once (D-100).
3. **Expiry parser** `backend/app/services/expiry_parser.py`: the spec's rules; all 35 cases of `tests/fixtures/expiry_cases.csv` as one test each (test date 2026-10-17).
4. **Other fields:** model or part number, size with units, name (strongest line that is not a date, model, size or boilerplate line).
5. **Gemini** `backend/app/integrations/gemini/`: REST `generateContent` through `httpx`, strict JSON schema, response validated, 20 s timeout, key in `/data/secrets/gemini.key` (0600, never returned, never backed up), `GET /gemini`, `PUT` and `DELETE /gemini/key`, `POST /gemini/test`; modes off / ask / auto; photos sent only when `share_images_with_gemini` is on. Settings section "Gemini" (P-02) with the disclosure text.
6. **Confirm screen** (P-07): source chips (Read from photo / Gemini / You), confidence dots, Re-read, Improve with Gemini (only when allowed), the "What was read" drawer, expiry "Not confirmed" until tapped, ambiguous dates as two pills, Save blocked with "Confirm the expiry date". The review queue shows the detected name and the reading state.
7. **Inspection interval** from Gemini is kept as a proposal labelled "suggested, unverified"; the maintenance toggle that uses it is Phase 4 (D-102).
Tests: unit (parser, fields, proposals, Gemini client against `httpx.MockTransport`), integration (extract flow, Gemini endpoints, key file rules), browser (confirm flow on a canvas-drawn label, Settings Gemini, crawler, contrast), probes 20 (network disabled) and 21 (`/health` under 200 ms while two readings queue). New dependencies: `rapidocr` and `onnxruntime` (and the engine's own requirements), `httpx` moves to runtime.

## Conflicts and gaps (decided by the authority order, CLAUDE.md 2)
1. **The engine must be chosen by measurement on the owner's 20 photos, and they do not exist yet.** Decision **D-099**: RapidOCR 3.10 on ONNX Runtime is the provisional engine (ONNX Runtime is on the allow-list; its PP-OCR models ship inside the wheel, so the image is offline from build time; no PyTorch in the app image). The bake-off script and its image target are built and smoke-tested now; the measurement table and the final choice wait for the photos (gate 2 BLOCKED). If another engine wins, only `integrations/ocr/engine.py` and the lock file change.
2. **When does local reading run, and who writes the read values into the form?** Not specified. Decision **D-100**: every new draft queues a local reading at once (the review queue already shows a reading state); Re-read queues another. The server keeps proposals apart from `fields`; the confirm screen fills each field the owner has not edited from its proposal and marks it with a source chip. A proposed expiry is saved with `expiry_confirmed: false` until the owner taps it. Proposals gain two optional keys: `alternatives` (the other reading of an ambiguous date) and `text` (the line the value came from).
3. **Which value wins when local reading and Gemini both propose one?** Decision **D-101**: Gemini's value replaces the photo reading's only where the photo reading has nothing or low confidence; Gemini's expiry text goes through the same parser, so the label rules (EXP vs MFD, day first) still decide the date. Gemini values never get high confidence and always carry the flag `unverified`. A category guess becomes a proposal only when it equals one of the owner's category names.
4. **The Gemini model default and the base URL.** Decision **D-102**: the default model is `gemini-3.5-flash-lite` (stable; checked on ai.google.dev 2026-10-24), changeable in Settings; the API base URL comes from `ENDERCHEST_GEMINI_URL` (default Google's) so tests point it at a closed local port and never call the real service. The suggested inspection interval stays in the draft's Gemini result for Phase 4.
5. **Gates that need the owner.** Gate 2 (20 real photos and confirmed `labels.csv`), gate 4 (a real Gemini round trip with the owner's key) and the acceptance run (webcam) are **BLOCKED** and listed under "Owner runs next". A canvas-drawn label and a mocked Gemini are regression tests only (D-056).
