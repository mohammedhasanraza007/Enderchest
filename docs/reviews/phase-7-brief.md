# Phase 7 brief — Camera coach

Written 2026-10-25 by the Phase 7 build session (chain, D-091: no "go" awaited).

## What I will build
1. **Client tier** (`frontend/src/lib/coach.ts`, pure and unit-tested): on a 320 px grayscale copy of every video frame, sharpness (variance of the 4-neighbour Laplacian), mean brightness, and glare (the largest 4-connected blob of pixels with luma above 250, as a fraction of the frame). Starting thresholds from the spec: blurry below 80, dark below 60, glare above 4%. They are recorded in the evidence log and tuned on the owner's real captures.
2. **Server tier** `POST /api/v1/capture/frame` (API 2.15): one JPEG of at most 200 KB, checked by its bytes, decoded in memory and never written to disk. The Phase 3 RapidOCR engine reads it through the shared size-1 heavy executor. The answer is `text_found` (at least 3 boxes with confidence ≥ 0.5), `confidence`, `boxes` (in fractions of the frame, with kind `text`, `model` or `date`), and `fields.model` and `fields.date` from the Phase 3 extraction. `busy` (409) and `rate_limited` (429) per D-121. The coach never calls Gemini, and frames never leave the machine.
3. **Client sender**: about once a second, only while the coach is on, the mode is Add or "Do I own this?", the stream is live, the tab is visible, and the latest frame passed both sharpness and light. It sends one 640 px JPEG with one request in flight. A `busy` or `rate_limited` reply drops the frame; any other error pauses sending for a while and the coach stays quiet (it is delight, never a blocker). Turning the coach off, changing mode or leaving the page aborts the request in flight.
4. **Prompt state machine** (pure, unit-tested): one prompt at a time, priority dark > blur > glare > no text > too far > found. A new prompt must hold for 300 ms before it shows, and a shown prompt stays at least 1.5 s. It is quiet when everything is fine. The prompt is a frosted pill (the nav material, opaque) near the bottom of the view, inside a polite live region. **Detection chips** ("Model number", "Date") sit on the picture where the server found them. Reduced motion is respected; only opacity changes.
5. **Settings → Camera coach**: a `coach_enabled` toggle (the setting already exists, so no migration and the schema stays at 4). With the coach off, no prompt, no chip and no frame request exist.
6. **Tests and probes**: unit tests (Python: frame route rules, busy and rate limits, box kinds; TS: metrics on synthetic pixels, the state machine and its timing, box mapping under `object-fit: cover`); integration tests (a real OCR read of drawn labels, 200 KB cap, non-JPEG refused, nothing stored, busy while a draft reading runs); e2e on Chromium's fake camera fed with generated MJPEG clips (dark, shaky, glare, empty, far, close) as a regression only, plus the coach turned off (zero requests) and never two requests in flight; probes 26 (`/health` under 200 ms while frames are read back to back, and no file appears under `/data`) and 27 (ten frames at once: OCR runs one at a time, the rest answer `busy` or `rate_limited`).
7. **Measurement for gate 1**: `test.bat coach` runs the client metrics and the server tier on the owner's labelled captures in `tests/fixtures/private/phase7/` and writes the table of expected against actual prompts to `docs/logs/raw/phase-7/coach/`. This is **BLOCKED** until the owner supplies the captures.

## Conflicts and gaps (settled in DECISIONS.md)
1. **D-120** Which modes get the coach: Add and "Do I own this?" (both take a photo to read). Scan mode keeps its own status line, because the QR decoder needs no label guidance and two prompts would compete.
2. **D-121** The shared size-1 executor queues work, but a frame waiting behind a three-second draft reading would be stale and would hold a request thread. So the frame route answers `busy` at once when the heavy worker has any job, and `rate_limited` when a frame comes within 500 ms of the last accepted one. Boxes are fractions of the frame, because API 2.15 gives no unit.
3. **D-122** The wording comes from DESIGN 9's table (at most 12 words), with a 1.5 s minimum on screen (the spec; it also meets DESIGN 9's 1.2 s). DESIGN 9's "Is that right?" after a date is dropped, because the coach cannot take an answer and the date is confirmed on the review screen. "Complete" is not shown, because the shutter leaves the camera for the review, which shows the fields. "Low confidence" is the no-text case with some unsure text.
4. **D-123** The client tier runs on every frame (the spec); PROJECT_PLAN 11's "about five times a second" is the older wording. "Move closer" is computed in the client from the boxes (median confident box height under 2% of the frame height), so API 2.15's response shape stays as written. A server answer older than 2.5 s counts as unknown.
5. **D-124** The shutter ring that "fills as the capture completes" and the pill's entrance motion are Phase 8 (motion, DESIGN 10). Phase 7 shows the pill with a plain opacity fade, and none under reduced motion.
